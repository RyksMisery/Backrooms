# Генератор областей — контракт чертежа и игрового превью

## Цель

`AreaSpec` — единый человеко- и машиночитаемый источник области. Один JSON
одновременно используется для:

- SVG-чертежа, который обсуждается и правится до реализации;
- occupancy-карты и автоматических проверок;
- игрового превью через канонические модули Godot;
- последующего размещения области в `level_e` с поворотом/зеркалом.

PNG/SVG не являются источником геометрии. Они всегда заново строятся из
`AreaSpec`, иначе семантика проёмов, глубина ниш и коллизии начнут расходиться с
игровой областью.

## Файлы

- спецификации: `areas/specs/<area_id>.json`;
- утверждённые чертежи: `areas/blueprints/<area_id>.svg`;
- отдельный игровой харнесс: `area_spec_preview.tscn`;
- загрузка и валидация: `modules/area_spec_module.gd`;
- сборка внутренней архитектуры: `modules/area_spec_builder_module.gd`;
- SVG: `modules/area_blueprint_module.gd`.

## Координаты

- Все горизонтальные координаты задаются в панелях, `CELL = 1.25 м`.
- Интерьер стандартной области занимает `[0, 15] × [0, 15]`.
- Координата клетки — её диапазон; центр клетки `i` равен `i + 0.5`.
- Оформленные дверные якоря всегда имеют дробную часть `0.5`.
- Перегородки лежат на именованной оси и не получают скрытых meter-offset.
- `axis = "z"` означает линию вдоль Z при постоянном X=`line`;
  `axis = "x"` — линию вдоль X при постоянном Z=`line`.

## Формат `AreaSpec` v1

Обязательные поля:

```json
{
  "schema_version": 1,
  "id": "mixed_hall_01",
  "size_cells": [15, 15]
}
```

Опциональные верхнеуровневые поля:

- `title`, `tags`, `notes` — каталог и обсуждение;
- `spawn_cells: [x, z]` — точка появления;
- `openings` — проёмы во внешней стене;
- `partitions` — внутренние осевые перегородки;
- `columns` — колонны;
- `wall_profiles` — локальная перестройка внешней стены;
- `occupancy_plan` — явная клеточная маска составной или нестандартной
  области. `origin_cells` задаёт координату левого верхнего символа,
  `rows` содержит строки одинаковой длины: `#` — стена, `.` — проходимый
  пол. Маска заменяет стандартную заготовку shell+interior и является
  источником одновременно для чертежа, коллизий и 3D;
- `light_regions` — список стандартных световых регионов
  `{origin_cells, size_cells, stride_multiplier}`. Каждый регион использует каноническую
  раскладку и clearance-проверку `lighting_module.gd`; локальные координаты
  светильников и их параметры в спецификацию не копируются.
  `stride_multiplier=2` означает штатную редкую сетку стандартного зала,
  `1` — плотную тестовую сетку с шагом `LIGHT_STEP`.
  `edge_inset_cells=1` сдвигает только первый и последний ряды региона на
  одну клетку к его центру, не меняя средние ряды.
  `trim_legal_rings=1` удаляет одно внешнее кольцо уже после occupancy-
  clearance; это позволяет убрать периметр фактической раскладки, даже если
  исходные крайние кандидаты ранее были отклонены стенами.
  `grid_phase_cells=1` сдвигает всю сетку региона на одну клетку по X/Z;
  применяется, когда оси светильников должны совпасть с осями проёмов, а не
  простенков;
- `light_overrides` — только явные локальные исключения. Поле `profile`
  принимает `tight` (default) или `wide`; широкий профиль использует
  канонические `range=10.0`, `attenuation=0.85`, `energy=0.42` из
  `lighting_module.gd`. `source_family=level_e_area` включает штатную
  семью `level_e`: прямоугольный `AreaLight3D` у панели, потолочный
  bounce-Omni и скрытый legacy-Omni для fallback. Параметры, вертикальные
  смещения и bounce-shadow pool берутся только из `lighting_module.gd`;
- `route` — ожидаемые вход/выход для проверки связности.

### Внешний проём

```json
{
  "id": "north_entry",
  "type": "opening_freeform",
  "side": "north",
  "center_cells": 7.5,
  "width_cells": 3.0,
  "height_m": 4.0
}
```

Типы совпадают с `docs/openings.md`:

- `doorway_raw`;
- `doorway_dressed_open`;
- `doorway_dressed_door`;
- `opening_freeform`;
- `fake_door_pocket`.

Калиброванные размеры оформленного проёма берутся из
`opening_module.gd`; JSON их не копирует. В v1 игровой builder поддерживает
`doorway_raw` и `opening_freeform` во внешней толстой стене. Остальные типы
разрешаются только после появления канонического конструктора кармана/створки
для толстой стены; валидатор обязан отклонять преждевременное использование.

### Перегородка

```json
{
  "id": "divider_a",
  "axis": "z",
  "line": 5.0,
  "from": 2.0,
  "to": 13.0,
  "thickness_cells": 0.5,
  "openings": []
}
```

Допустимые канонические толщины v1: `0.25`, `0.5`, `1.0`, `2.0`. Проёмы
перегородки используют те же типы и якоря, но `side` им не нужен. Офисное
оформление разрешено только на перегородке `0.5 CELL`; дверь и рамы создаются
`opening_module.gd` из одного `opening_id`.

### Колонна

```json
{
  "id": "column_a",
  "shape": "rect",
  "center_cells": [4.0, 4.0],
  "size_cells": [2.0, 2.0]
}
```

В v1 реализован прямоугольник. Крест, Т/Г-краевые варианты и шумовые парные
колонны добавляются отдельными именованными shapes после переноса их
конструкторов из compatibility-базы в канонический модуль.

### Профиль стены

`portal_recess` использует существующий канонический профиль архитектурного
модуля: `sides`, `side_margin_cells`, `top_margin_cells`, `depth_cells`,
`center_divider_cells`. Проём-карман и слепое фальш-окно остаются отдельными
семантическими типами и не имитируются портальным углублением.

## Чертёж

SVG обязан показывать:

- внешний трёхклеточный shell и интерьер `15×15`;
- клеточную сетку и координаты;
- реальную толщину перегородок и размеры колонн;
- проёмы, их направление, тип и `opening_id`;
- световые клетки после clearance-проверки;
- spawn и найденный маршрут между назначенными сокетами;
- ошибки и предупреждения спецификации.

Цвет является представлением семантики, а не входными данными.

Для растрового прототипа инверсия цветов выполняется до фиксации
`occupancy_plan`: после утверждения чёрный означает `#`, белый — `.`;
неопределённых серых клеток в источнике геометрии быть не должно.

## Валидация v1

До построения 3D обязательны проверки:

1. схема и размер `15×15`;
2. уникальность всех `id`;
3. допустимые стороны, оси, типы и толщины;
4. попадание всех элементов в интерьер;
5. сеточный якорь дверного класса;
6. отсутствие пересечения spawn с препятствием;
7. достижимость назначенного входа и выхода по клеткам;
8. отсутствие светильников в препятствии и восьми соседних клетках.

## Эксперимент: защита от света за перегородкой

До отдельного визуального допуска это правило действует только в AreaSpec и не
является каноном `docs/lights.md`. Опциональный блок
`light_overrides.partition_guard` оценивает каждую штатную позицию светильника:
считает клетки пола в пределах экспериментального effective reach, луч к
которым пересекает глухую перегородку или колонну. Такие клетки требуют тени и
увеличивают риск засвета при переполнении LF3-пула.

```json
"light_overrides": {
  "profile": "wide",
  "partition_guard": {
    "mode": "filter",
    "effective_reach_m": 5.0,
    "max_cross_partition_cells": 0
  }
}
```

`mode=off` оставляет прежнюю раскладку, `warn` только показывает риск на
чертеже и в отчёте, `filter` исключает позицию, если число зависимых клеток
выше допуска. `effective_reach_m` намеренно не равен автоматически физическому
радиусу Omni: это тестируемый порог визуально значимого вклада. На сравнительных
конфигурациях проверяются как минимум сплошная перегородка, перегородка с
проёмом, короткий stub и источник, отнесённый глубже допустимого reach.

Чертёж показывает исключённые позиции красным крестом. Эксперимент считается
удачным только если в 3D уменьшаются засветы без неприемлемых тёмных провалов;
после этого отдельно выбираются порог и способ переноса в общий канон.

Для одного и того же JSON тестовый preview принимает аргумент
`--light-guard-reach=<метры>`, а генератор чертежа — тот же аргумент вместе с
отдельным `--out`. Это только A/B override харнесса: сохранённая спецификация
остаётся источником основной конфигурации. Стартовый sweep пилотной области:
`3.75 / 5.0 / 6.0 / 7.5 / 10.0 м`; default теста — `5.0 м`.

В `area_spec_preview.tscn` клавиша `0` выполняет прямое A/B-переключение
раскладки: `GUARD OFF` возвращает все штатные позиции, `GUARD ON` применяет
`partition_guard` из текущей спецификации или command-line override. При
переключении сохраняются позиция, направление взгляда и скорость игрока;
геометрия, широкий профиль источника и LF3-11F не меняются.

### A/B-бот partition guard

Машинный прогон эксперимента запускается только в настоящем Forward+ окне:

```text
Godot --path . --script res://tools/run_area_light_ab.gd
```

Runner снимает одинаковые пары `GUARD OFF | GUARD ON` для лицевой и обратной
сторон длинной перегородки, короткого тяжёлого stub и поперечной перегородки.
Для каждого вида сохраняются полный кадр, contact sheet, общая яркость,
яркость центральной и боковых ROI, RGB MAE и состояние LF3 shadow-пула.
Внутри пары область не перестраивается: runner атомарно меняет энергию только
отклонённых источников `canonical ↔ 0` и видимость соответствующих эмиссивных
панелей. Свойство `OmniLight3D.visible` не используется, потому что повторное
включение источника даёт зависимый от renderer state результат. Environment,
геометрия, материалы, камера, игрок и оставшиеся источники сохраняют идентичность.
Каждый ракурс проходит последовательность `OFF₁ → ON₁ → OFF₂ → ON₂`; совпадение
повторных состояний отделяет реальный эффект раскладки от temporal-сходимости и
порядка GPU-захвата.

Динамическая часть дважды проходит один маршрут вперёд/назад при неизменном
направлении камеры: на пилотной раскладке `OFF/ON` и на отдельной открытой
16-ламповой конфигурации, где гарантированно проверяется граница 10/11. Отчёт
фиксирует пик активных теней, число кадров с временной 11-й тенью, смены
идентичности caster, максимальный шаг opacity, симметрию одинаковых координат,
стабильность неподвижного состояния и frame time. Пик выше 11, расхождение
вперёд/назад или изменение тени при неподвижном игроке являются машинным
провалом. Снижение засвета и допустимость новых тёмных провалов остаются
решением по сохранённым изображениям.

Артефакты записываются в `.area_light_ab/<timestamp>/`; каталог диагностический
и не является частью AreaSpec или светового канона.

Контрольный Forward+ прогон `2026-07-22T18-19-01` не допустил правило в канон.
На пилотной области `OFF/ON = 8/5` ламп; во всех четырёх ракурсах каждый
occupancy-risk источник уже имел тень (`unshadowed_risky_lights=0`), поэтому
переполнения LF3-пула и доказанного пробоя для исправления здесь не было.
Фильтр уменьшил число смен caster `10→4` и максимальный шаг opacity
`0.461→0.217`, но визуально дал преимущественно общее затемнение: эффект на
центре перегородок лежал от `0%` до примерно `-1.5%`, на отдельных боковых ROI
до `-8%`, а тяжёлый stub в центральной ROI не изменился.

Отдельный 16-ламповый stress подтвердил runtime LF3: пик `11` теней, временная
11-я была активна `80/194` кадров, расхождений вперёд/назад и неподвижного
дрейфа нет. Максимальный шаг opacity отдельного caster `0.540` сам по себе не
является визуальным pop: для решения нужен следующий фиксированный image-
sequence на конфигурации, где одновременно есть перегородка и более 11
risk-источников. До такого теста `partition_guard` остаётся только ручным A/B
экспериментом AreaSpec.

Повторные статические прогоны также обнаружили renderer-state зависимость при
runtime-выключении и возврате источников: состояние shadow-пула восстанавливается,
но пиксельный вклад части Omni может зависеть от истории clustered-light list.
Поэтому итоговый художественный A/B выполняется клавишей `0`, где область
пересобирается из спецификации; внутренний атомарный toggle бота используется
только для диагностики и проверяется повторными кадрами.

Валидатор не исправляет спецификацию молча. Любое округление или подмена
элемента запрещены; автор получает ошибку с `id` объекта.

## Рабочий цикл

1. Создать или изменить JSON.
2. Запустить validator и генератор SVG.
3. Обсудить чертёж и внести правки в JSON.
4. Запустить `area_spec_preview.tscn` и проверить масштаб от первого лица.
5. После утверждения пометить спецификацию тегом `approved`.
6. Только утверждённые спецификации становятся кандидатами каталога `level_e`.

## Граница первой итерации

Первая итерация доказывает полный цикл на одной области: внешние свободные
проёмы, прямоугольные колонны, осевые перегородки, автоматический свет, маршрут,
SVG и 3D-превью. Расширение типов ниш и колонн выполняется после этого
вертикального среза без изменения формата уже созданных областей.
