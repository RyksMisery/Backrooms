# Профильные проверки и визуальные эталоны

Этот документ определяет минимальную проверку изменений без полного прогона
проекта. Он применяется вместе с `docs/agent_workflow.md`: одна задача получает
только относящийся к ней профиль.

## Основной принцип

Технический маркер `*_OK` доказывает только выполнение проверяемого контракта.
Он не является визуальным допуском. Изменение, влияющее на изображение или
переход между состояниями, принимается только при одновременном выполнении двух
условий:

1. профильный структурный валидатор завершился успешно;
2. контрольный маршрут не показывает пользовательский дефект.

Если подход не прошёл визуальный допуск, агент не пишет `Готово`, отключает или
откатывает принадлежащий подходу слой и фиксирует результат в профильном журнале
экспериментов.

## Визуальный эталон

Для каждого принятого сложного узла хранится компактный набор эталонных видов,
а не длинная запись всего прохождения. Эталон должен включать только кадры,
которые способны обнаружить характерную регрессию:

- общий вид до взаимодействия;
- критическая поверхность крупно: пол, стена, потолок или край проёма;
- для перехода — непрерывная серия `N-2`, `N-1`, `N`, `N+1`, `N+2` вокруг
  момента переключения без ожидания стабилизации;
- один косой угол и одно боковое смещение, если эффект зависит от параллакса;
- короткая неподвижная выдержка, если возможны мерцание, миграция или поздняя
  активация.

Кадры снимаются при детерминированных позиции, ориентации, состоянии области и
профиле качества. Эталон создаётся только после явного принятия результата
пользователем. До принятия артефакты остаются диагностическими и не становятся
новой нормой.

Сравнение выполняется в два этапа:

1. автоматическое — размеры, наличие кадров, состояние runtime и грубая
   разница изображения;
2. визуальное — поверхность, свет, тени, края, clipping и однокадровые скачки.

Автоматическая близость изображений не отменяет визуальный дефект. При
преднамеренном изменении картинки старый эталон заменяется только после
авторского принятия новой версии.

одна узкая проверка, затем она добавляется в таблицу.

## Правила запуска

- Запускается только строка матрицы, которую затрагивает изменение.
- Полный визуальный бот не запускается, если пользователь прямо запретил его в
  текущей задаче.
- Для локальной правки достаточно одной профильной проверки.
- Для сложного дефекта диагност сначала доказывает причину минимальным тестом;
  полный визуальный маршрут запускается после исправления, а не после каждой
  гипотезы.
- При изменении нескольких систем их проверки перечисляются до правки; новые
  несвязанные проверки не добавляются по ходу работы без обнаруженной причины.
- Команды выполняются из корня проекта только на Godot 4.7 stable.

## Контрольные коммиты

После явного принятия самостоятельного состояния допускается один небольшой
локальный commit с понятным названием. В него входят только файлы принятого
изменения и его документация. Несвязанные изменения пользователя не добавляются
и не откатываются.

Экспериментальные итерации не требуют commit на каждый параметр. Перед
архитектурным экспериментом фиксируется точка отката, а commit создаётся после
одного из двух результатов:

- способ принят;
- способ полностью удалён, а причина отказа документирована.

Push, публикация и переписывание истории выполняются только по отдельному
решению пользователя согласно порогу безопасности.

## Формат задания помощнику

Claude или другой вспомогательный агент получает короткий пакет:

- цель и наблюдаемый дефект;
- разрешённые файлы и маршрут;
- запрещённые изменения и запуски;
- одну проверяемую гипотезу либо просьбу сформулировать её;
- критерий готовности;
- требуемый формат ответа.

Ответ помощника ограничен четырьмя блоками: `вывод`, `доказательства`, `точные
места`, `следующий минимальный тест`. Пересказ документации, альтернативы без
доказательств и самостоятельная правка продуктовых файлов не принимаются.

## Выбор состава

- Известная причина и локальная правка — только Кристалл.
- Неизвестная причина — Кристалл и один read-only диагност.
- Визуально сложный результат — после правки добавляется один независимый
  проверяющий.
- Архитектурная гипотеза — изолированный стенд; продуктовый писатель остаётся
  один.
- Более двух помощников допускаются только для действительно независимых
  подсистем в разных задачах и ветках.

Параллельность применяется для независимого получения доказательств. Она не
заменяет ясную гипотезу и не используется как способ перебрать больше случайных
решений.
