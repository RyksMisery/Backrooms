# План: вариант 2 — областной билдер на единой occupancy-сетке

Рабочий трекер для нового варианта генерации. Ведём прямо здесь:
отмечаем сделанное, фиксируем отклонённое/изменённое.

## Легенда статусов

- `[ ]` — не начато
- `[~]` — в работе
- `[x]` — сделано
- `[-]` — отклонено / заменено (с пометкой почему в журнале ниже)

## Базовые принципы (зафиксировано)

- `level_blueprint.gd/.tscn` — **заморожен**, остаётся как «вариант 1»
  (эталон архитектуры/света). Не трогаем.
- Новый вариант — отдельный файл (`level_areas.gd` + сцена), ничего не
  ломает в блюпринте; можно подсматривать раскладки и материалы.
- Порядок перевёрнут: **сначала логическая occupancy-сетка, из неё — вся
  геометрия, карта и свет** (один источник правды).
- **Элементы и контейнеры — разные сущности.** Проёмы, двери, колонны,
  перегородки — переиспользуемая библиотека, кладёт данные в сетку и не
  знает, в какой области находится.
- «Офис» — не особый тип геометрии, а область, населённая перегородками и
  проёмами.
- Колонна — генерируемый элемент (1×1, 2×2, 3×3, 3×2). Колонный зал — его
  авторская/шаблонная раскладка (хардкод вариантов), чтобы избежать мешанины.
- Плотность заполнения области — низкая и параметризуемая: «лабиринт в
  лабиринте» без перегруза.
- Два сида с самого начала: `seed_topology` (граф + типы + повороты),
  `seed_detail` (перегородки + состояние проёмов).
- Свет: интерфейс пула закладываем сразу с полем `casts_shadow` у световой
  клетки. Логику переносим как есть, культинг теней включаем позже.

      `level_areas_c.gd`. Форма блока ФИКСИРОВАНА, не рандомится: сплошной

      tree) решает ТОЛЬКО связность — какие стыки между 9 клетками открыты,

      `maze_wilson`, просто масштаб другой (целые области, не панели). Сеед —
      `seed_topology` (отдельный от `maze_seed`).

      четвёртой (южной) стороне брэнчера `cor_s_e` — у `branch`

      изнутри отсек — снаружи дыра в стене есть, но дойти до неё нельзя.
      Держать в уме для любой будущей стыковки: у `branch` только 3 честные
      стороны, четвёртая — не для новых проходов. Угловые `lit_hall` внутри
      только пилястры, без перегородок — обе свободные стороны честные,
      безопасная точка стыковки для новых веток.
      До `MACRO_DFS_MAX_LOOPS` (2) коротких петель поверх остова
      (`MACRO_DFS_BRAID_P` 0.15) — жёсткий лимит, не 10-15% как в общем

      generic-помощник `_carve_area_link` (существовал, ранее не вызывался).
      Старый черновик `_empty_maze_links` (см. выше) не трогали и не оживляли.
      **Столбец `x=3` (южнее угла `(3,3)`) выведен из DFS-обхода и
      зарезервирован под фиксированную цепочку `_append_south_chain`/
      `_carve_south_chain`:** хаб `(3,3)` → двойной (по Z, 2 слитые области)

## Журнал решений (отклонено / изменено)

> Сюда записываем, от чего отказались и почему, что поменяли по ходу.

- Тени интерьерных props: реалтайм-тень от потолочной лампы плоская и
  «парит». Решение — **контактная тень-декаль** (мягкое пятно на полу) для
  привязки к поверхности + реалтайм-пул только для объёма.
- Поппинг теней при ходьбе (пул пересчитывался каждый кадр) → добавлен
  **гистерезис** переключения кастеров (margin 2.5 м).
- Акцентные объекты (стул с игровым/психологическим смыслом) — отдельный
  узкий луч-прожектор сверху. Отложено, делаем когда дойдём до props-системы.
- Тест-область `maze_wilson` (лабиринт по остову Уилсона + braid): первая
  прикидка ячейка=1 панель отклонена — на практике проходы иногда физически
  непроходимы. Закреплено правило — ячейка ≥ 2 панели (сейчас 6×6, 2.5
  панели). По ходу нашлись и починены два общих бага, актуальных для любой
  похожей мелкоячеистой конструкции: (1) на стыке двух перегородок, где
  ширина проёма равна шагу сетки, нужен явный столбик-«пятак» в узле —
  иначе видимая выемка; (2) свет нельзя ставить через общий
  `_light_blocked`/`_add_grid_lights` — он метит блоком всю линию
